    How Literally Should ProbOS Take "Ledger"?¶

    Status: Design note; the Captain's decisions of 2026-10-30 are in section 7. Step 1 of the sequence in section 6 (BF-942) is done and step 2 is next. Not an AD; it allocates no number and creates no work by itself. Drafted by: claude-architect (Claude Code, Opus 5.5), 2026-10-30. Verified against main at 1ffbdc61. Revised by: claude-architect (Claude Code, Opus 5.5), 2026-11-27, for the BF-942 fix. Re-verified against main at 32997b18: every statement about BF-942 and BF-980, the "Verified in production?" and "Known gaps" cells of the EventLog, Identity Ledger, security AuditLog and Ship's Records rows, section 6's step 3 candidates, and every citation into a file that changed since 1ffbdc61 (event_log.py, runtime.py, startup/finalize.py, records_store.py, config.py, config_models/knowledge.py, acm.py, workforce.py, routers/workforce.py, admission/store.py) or did not exist then (doctor/checks/records_git_check.py), and the four records step 1 names (prompts/bf-942-eventlog-truncation-anchor.md, PROGRESS.md, DECISIONS.md, deterministic-ship.md). Citations into the other files, unchanged since 1ffbdc61, stand as verified then. Placement: a companion to Probabilistic Crew, Deterministic Ship, invariant 4 ("a fixed past").

    Question (the Captain's). The thesis of the deterministic ship speaks of "a system of record, like a ledger". How literally should ProbOS take that? Does it already have a ledger, should it have one, and is this a use case for blockchain?

    1. Short answer¶

    • ProbOS already keeps ledgers, plural. Three stores are hash-chained (the EventLog, the Identity Ledger and the security AuditLog), Ship's Records is a git repository, and about a dozen other tables are append-only by rule. "Ledger" is already literal in the sense that matters: an append-only record whose past entries are not rewritten.
    • What it lacks is one thing a ledger implies: the ability to prove the whole record is unchanged. The EventLog's chain survives pruning since BF-942 (#1706, fixed 2026-11-09), but no production code verifies it; the Identity Ledger is verified on request, the security AuditLog at boot, and nothing ties the separate stores together. Every guarantee is held on the same disk as the data it protects.
    • The literal step worth taking is small: a ship's log of chain heads. Every so often, record each store's current head hash in one append-only, hash-chained record, signed with the ship's key when one is configured. Then copy that head off the ship to a witness. Without a witness it protects against bugs and stray writers, not against anyone who controls the machine.
    • No blockchain inside a ship. A blockchain is a way for parties who do not trust each other, and have no common authority, to agree on one history. A ship has one authority, the Captain, on one install. A blockchain would add cost and latency and would collide with the Captain's right to erase (AD-754).
    • Between ships, use a transparency log, not a blockchain. Ships run by different operators are where blockchain-like properties start to matter. The established answer there is a Certificate-Transparency-style log: a Merkle tree, signed tree heads, and independent witnesses. ProbOS's DIDs, Ed25519 key binding and signed identity chains (AD-1196 to AD-1198) already point that way.

    3. The gaps¶

    1. A chain broke in normal operation; closed 2026-11-09. EventLog pruning severed the AD-490 chain. BF-942 (#1706, PR #1778) leaves the kept rows unchanged, since rehashing them would forge history, and records a durable truncation anchor like AD-1278's in the transaction of each prune's delete (event_log.py:1337-1419). The anchor is held in events.db with the rows, so gap 4 applies to it.
    2. Verification is patchy and silent. The EventLog is never verified, the Identity Ledger only when someone asks, and the AuditLog at boot with a warning nobody is alerted to. Under invariant 6, a check that never runs or that reports only to a log is close to no check.
    3. Each ledger stands alone. Nothing proves that the EventLog, the identity chain, Ship's Records and the Archive, taken together, are the history the ship had yesterday.
    4. Every proof lives on the same disk as the data. Anyone who can rewrite a store can rewrite its chain too, and restoring an old backup of the whole data directory rolls back the chain along with the data. A hash chain only detects tampering when someone else holds a copy of a recent head. This is the core of the tamper-evident logging literature (Crosby and Wallach, 2009) and of Certificate Transparency's witnesses and gossip.

    4. Proposal: a ship's log of chain heads¶

    What. One append-only store, the head log. Each entry, called a checkpoint, records for every covered store its name, its current head, and the size or position at that head. Each checkpoint also carries the hash of the previous checkpoint and the time. When the ship's key is configured (AD-1196), the checkpoint is signed with it as a detached JWS (AD-1144). Otherwise it says plainly that it is unsigned.

    What "head" means per store (version 1):

    Store Head Cost to read
    EventLog (id, row_hash) of the last row, plus the truncation anchor (BF-942) One indexed read
    Identity Ledger (block_index, block_hash) of the tip One read
    Security AuditLog (sequence, entry_hash) of the last persisted entry, plus _truncated_at In memory
    Ship's Records git rev-parse HEAD, plus whether the working tree is clean One subprocess

    Version 1 covers only stores that already have a chain. The others (Archive, ACM transitions, trust receipts, booking timestamps, calibration, the snapshot ledger) have no head to record. Bringing them in means giving each one a chain, or having the head log chain them by recording a digest of the rows added since the last checkpoint. That is version 2, and it runs straight into erasure (open question 3).

    Verification. A verifier walks each store's chain from its anchor, confirms that the head recorded in every checkpoint is reachable in the current chain, and checks the head log's own chain and signatures. It reports one state per store: intact, truncated at an anchor, broken at a position, or not verified, never a bare pass (invariant 6). It runs at boot, as the AuditLog check already does, then on a schedule and on demand from a CLI or doctor command. The Captain sees the latest checkpoint, its head digest and the last verification result. A failure needs a real alert, which no chain has today.

    The witness, which is what makes it more than a checksum. The checkpoint digest must leave the ship. In rising order of cost: the Captain copies or exports it (a short digest shown in the HXI or CLI); a federation peer countersigns it over the signed envelopes AD-1197 already provides; or an RFC 3161 timestamp authority or OpenTimestamps timestamps it, which sends a 32-byte hash and no data. A witness turns "the store says it is intact" into "the store still matches what someone outside saw on that date", and it also detects a rollback of the whole data directory.

    What it defends against. Bugs that delete or rewrite rows (the BF-942 class), writers that bypass a store's owner (BF-943 is the file-level cousin), and a silent restore of an older backup. It does not defend against the Captain: the Captain owns the ship and may erase, which is why erasure has to be designed in rather than treated as tampering.

    Cost. One small row per checkpoint; reading the version 1 heads is a handful of indexed reads and one git call. A full verification is linear in chain length; the EventLog is capped at 100,000 rows by default. Witnessing costs a network call per checkpoint, or none if the Captain copies the digest by hand.

    Open questions for the AD that builds it¶

    1. Signing key and owner. The ship's DID key exists only when federation.identity_keys_enabled is on (default off), held in the OS keyring (identity_key_store.py:119) or, in development, in plaintext (:209). Should the head log require it, sign when available, or use a separate local key? A local signature adds little against someone who holds the machine; its value is that a third party can verify an exported checkpoint.
    2. Where it lives. Its own SQLite file through ConnectionFactory, beside the stores it covers, and owned by one service. It must survive probos reset, as the Archive does, and a reset should close the old timeline with a final checkpoint that the new timeline's first checkpoint cites.
    3. Erasure. The Archive's erase marker deliberately keeps no hash of the erased entry, because a hash of short or guessable content can confirm what it was. A version 2 digest over Archive rows would break when an entry is erased. Options: (a) leave erasable stores out of the head log; (b) give each row a random salt and commit only to H(salt, content), deleting the salt on erase, so the commitment survives but reveals nothing, a known pattern for erasure on append-only logs (EPRS, 2019); (c) record an erasure as a new head with a signed reason and accept that the erased segment can no longer be re-verified. Option (b) changes the Archive's "no hash" rule, so it is the Captain's call.
    4. Retention. With BF-942's anchor, every checkpoint older than the anchor refers to rows that are gone. The verifier should report such checkpoints as "covering pruned history" and check only that the anchor sits on the recorded path. The signed head log is also what keeps the anchor itself from being forged: an attacker who rewrites rows and resets the anchor no longer matches earlier checkpoints.
    5. Which governance files count. BF-943 shows agents can rewrite governance files in the running checkout. A git tree hash of config/standing_orders/ and the Constitution would fit in a checkpoint. Considered and deferred: BF-943's write floor is the first defence.
    6. Interval. A fixed interval (hourly, matching the prune loop) or at defined events (boot, shutdown, prune, reset). Events are cheaper and give natural points to verify against.

    5. Is this a use case for blockchain?¶

    Inside one ship: no. A blockchain (Nakamoto, 2008; or a permissioned BFT ledger) solves one problem: getting mutually distrusting parties with no common authority to agree on one append-only history, through proof-of-work or validator voting. Remove that problem and what remains is a hash chain, which ProbOS already has. A ship has a common authority, the Captain, and one install. Running a consensus protocol among processes that share an owner, a disk and a key buys nothing a hash chain plus a witness does not, and it costs latency on every commit point, operational complexity and a large new dependency.

    It would also collide with two things ProbOS chose deliberately:

    • The Captain's right to erase. AD-754 erasure and the Archive's content-free erase marker exist so that data the Captain asks to forget is actually gone. An immutable replicated ledger is built to make that impossible; the European Parliament's study on blockchain and the GDPR describes this as a structural tension and recommends keeping personal data off-chain (Finck, EPRS, 2019).
    • Two meanings of "consensus". ProbOS's consensus (QuorumEngine, trust-weighted votes on destructive intents) is judgement: should this happen? Blockchain consensus is storage agreement: what order did things happen in? Using the second to stand in for the first, or the reverse, would blur the line deterministic-ship.md draws between what is probabilistic and what is recorded.

    Between ships: blockchain-like properties matter; a blockchain still is not the best tool. Ships run by different operators do not share an authority, so one ship's history is a claim another ship must be able to check. That is exactly the setting Certificate Transparency was built for: independent logs, append-only Merkle trees, signed tree heads, inclusion and consistency proofs, and monitors and witnesses who compare what they were shown, so a log cannot show different histories to different parties (RFC 6962, now RFC 9162). Sigstore's Rekor applies the same design to software signing, now on a tile-based log, with witness cosigning in progress. It needs no mining and no token, and each ship stays the only writer of its own log.

    What the federation ADs already provide, and where this fits:

    • AD-441, AD-443: did:probos identifiers, birth and transfer certificates, and an exportable, importable Identity Ledger chain.
    • AD-1196: the ship's DID bound to an Ed25519 key, with rotation and recovery, as key events anchored in that chain.
    • AD-1197: canonical signed envelopes with replay protection.
    • AD-1198: authenticated peer admission, chain resync, and verification of every chain relied on.

    Together they give each ship a signed, verifiable identity history that its peers check. What they do not give is a peer that remembers another ship's head and would notice a fork or rollback later. The envelope store keeps a forward-only hold of each peer's key events, which is the start of that. A federation transparency log would extend it: each ship publishes signed checkpoints of its head log, and peers countersign them as witnesses. Epic #1140 (AD-1196 to AD-1198) is closed, so this needs a new issue when federation work resumes; it does not belong under

    1140.¶

    Optional public anchoring. A ship may periodically timestamp its checkpoint digest on a public chain (OpenTimestamps) or with an RFC 3161 authority. Only a 32-byte hash leaves the ship, so it conflicts with neither erasure nor privacy. It proves only "this digest existed by this date", which is the one thing a single ship cannot prove to itself.

    6. Recommended sequence¶

    1. BF-942 (#1706). Done on 2026-11-09. A durable truncation anchor for the EventLog, after the AD-1278 pattern, merged in PR #1778 and recorded in prompts/bf-942-eventlog-truncation-anchor.md, PROGRESS.md, DECISIONS.md and invariant 4 of deterministic-ship.md. BF-980 (#1811, PR #1831, 2026-11-18) chains the first row after a prune that empties the table from that anchor.
    2. Verify what exists and say so. The next step. One verification service for the three chains plus git fsck on Ship's Records, run at boot and on demand, reporting intact, truncated, broken or not verified, with a Captain alert on failure. This also takes on the AuditLog's missing alert. It could be a BF or a small AD. What unanchored means to an operator (history cut and no anchor records where, as in a store pruned before BF-942) is not decided; it is decided before verify_chain is wired to a doctor check or an integrity report (BF942-F4, #1754).
    3. Fix the false "append-only" claims found here. Booking timestamps deleted by delete_work_item: a candidate BF, not filed by 2026-11-27; file it only after confirming reach. The second candidate, Ship's Records' commit failure logged at debug, was fixed by BF-957 (#1760, closed 2026-11-08): it is now logged at WARNING and probos doctor reports the repository's state, and it is still not raised (records_store.py:1990-1994).
    4. The head log (a future AD). Version 1 over the chained stores, with a manual or RFC 3161 witness.
    5. Version 2 coverage of the Archive and other append-only tables, after the erasure decision below.
    6. A federation transparency log, as a new issue when federation resumes, built on AD-1196 to AD-1198.

    7. Decisions (Captain, 2026-10-30)¶

    The Captain took the recommended option on all five:

    1. The head log is adopted as a future AD, to be filed after steps 1 and 2 (BF-942, then verification with an alert). It is small and makes invariant 4 checkable.
    2. Witness: start with the Captain's own copy of the digest, plus an optional RFC 3161 or OpenTimestamps anchor. Peer witnesses come only with federation.
    3. Erasure versus coverage: the Archive keeps its "no hash of erased content" rule and stays out of the head log for now. Salted commitments (option b in section 4) are not adopted.
    4. Signing: the head log is signed only when the ship's key is configured, and records say "unsigned" otherwise. The key is not a prerequisite.
    5. Blockchain: ProbOS uses hash chains and transparency logs, not a blockchain, unless a future need appears for agreement among parties with no common authority.

    Status, 2026-11-27. Step 1 of the sequence in section 6 is done: BF-942 (#1706) was fixed on 2026-11-09 (PR #1778). Step 2, verification with an alert, is next. The head-log AD is filed only after step 2 (decision 1).

    8. Prior art¶

    • S. A. Crosby and D. S. Wallach, "Efficient Data Structures for Tamper-Evident Logging", USENIX Security 2009 (USENIX). Adopted: detection needs a commitment held outside the logger. Deferred: their history tree, with logarithmic proofs, is worth using only when a third party audits (federation).
    • B. Laurie, A. Langley, E. Kasper, RFC 6962 (2013), and B. Laurie, E. Messeri, R. Stradling, RFC 9162, Certificate Transparency 2.0 (2021) (RFC 9162). Adopted as the model for federation: Merkle tree, signed tree heads, consistency proofs, and monitors.
    • Trillian and Sigstore Rekor (Rekor v2 moved to a tile-based Trillian-Tessera log; witness cosigning is in progress) (Sigstore blog). Considered: reference implementations if ProbOS ever runs a shared federation log; too heavy for one ship.
    • Git as a Merkle DAG: every commit hashes its tree and parents, so Ship's Records already has a chain whose head is the commit id. Adopted: use it as is.
    • C. Adams et al., RFC 3161, Time-Stamp Protocol (2001), and OpenTimestamps (P. Todd). Adopted as optional external timestamps that send only a hash.
    • M. Finck, Blockchain and the General Data Protection Regulation, EPRS/STOA, PE 634.445, July 2019 (PDF). Adopted: keep personal data off any immutable shared log; erasure needs designing in.
    • Internal: no earlier ProbOS design of a Merkle tree, transparency log or blockchain. The only mentions are the "hash-chain blockchain" wording above, the warm-boot design note's use of the EventLog chain as a tamper-evident witness (docs/research/warm-boot-fragmentation-design.md:34), and the Nooplex vision's discussion of DAOs and token-curated registries as cross-organisation governance (Vibes/Nooplex_Final.md:141), which this note leaves to federation.
    • Not fetched in full here (the hosts were unreachable from this session): the RFC 9162 text itself and the Crosby and Wallach paper. Their summaries above rest on the RFCs' and paper's well-known content and search abstracts.
