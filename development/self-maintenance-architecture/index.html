    AD-1299 - ProbOS Self-Maintenance Architecture¶

    Status: planned, not implemented. This is an OSS architecture decision, not an active repair campaign or permission to start one. No runtime, deployment, governance policy, or campaign state changes are authorized here.

    Rescope 2026-10-11 (native owners). The Captain retired the Supervised Worker integration on 2026-10-10. This document now names native ProbOS owners for campaign state, authority, review, execution backends and release. The requirements that stood (separate grants, isolated build, independent review, immutable promotion, verified rollback, no in-place patching) are unchanged. D-B2 was reframed the same day (see "D-B2: reframed 2026-10-11"): no candidate code runs before the Captain approves its exact candidate digest, and agents may prepare candidates as text without the Captain; whether any campaign may run candidate code or advance a repair action without that approval remains the Captain's decision, with option (a), keep execute-after-approval, as the working default S1-S4 build under. Recorded in the append-only decision record under "Native rescope (2026-10-11)".

    Tracking: Epic #1352. See the roadmap and the append-only decision record.

    Purpose and boundary¶

    A Utility-tier ProbOS Engineering Maintenance Agent diagnoses, repairs, maintains, and enhances ProbOS by composing its existing engineering and self-modification systems. It is an instructions-first CognitiveAgent, not another coding loop, scheduler, or root of trust. Its proposed implementation name is EngineeringMaintenanceAgent; this document does not claim that class is already implemented.

    Governance is native and honest about its strength. Campaign identity and lifecycle live in the existing CrewSession/WorkItem owners; authority is the Captain's decision on an action-shaped approval, bound to one candidate digest, per consequential step; release activation is an out-of-process controller the Captain invokes. ProbOS cannot authorize its own promotion: it holds no promotion entry point.

    What is enforced and what is only detected. Enforced: a human decision at every consequential step, compare-and-set state transitions in the existing stores, a controller process that does not depend on ProbOS being alive, and generation-checked activation and rollback. Refused: a receipt or review set that contradicts the candidate in the facts the binders check (commit, tree, status, schema and reviewer independence, plus the label when one is expected). Recorded, not refused: a sha256 for each piece of evidence; for a receipt, the SHA-256 of the supplied raw bytes, so any change to those bytes changes it; for a review set, a domain-separated SHA-256 of the candidate-bound projection of five review fields (attempt id, reviewer id, assignee id, reviewed tree, accepted), so a change to those five fields changes it and a change to any other review attribute does not. A consumer that retained an earlier trusted digest can therefore detect a change within what each digest covers. Not authenticated: the evidence's producer; unread fields are not asserted valid. Not prevented: writes by any process that runs under ProbOS's own OS identity to ProbOS state, the release root or the evidence (AD-1315 Boundary: local-host evidence, not a defense against administrator/root/kernel compromise). Not contained: candidate code that a campaign runs (tests, shadow run) executes under the Captain's OS identity, so approval decides what runs but does not confine it. Excluding same-identity writers needs a separate owner identity or OS isolation with privileged provisioning; that is D-B2 option (b), the Captain's decision.

    Existing foundations and measured limits¶

    These are inspected source contracts, not a claim that a running vessel has exercised the proposed end-to-end path.

    The closed self-diagnosis and repair epic #1095 owns AD-1166 through AD-1173. Its closure records the shipped fault/diagnose/repair loop; its original problem statement is historical, not a current absence claim. AD-1299 extends those foundations with governed campaigns and immutable runtime promotion rather than reopening or duplicating them.

    Measured gaps. There is no promotion or rollback step in the native repair loop and no release, updater, promotion or rollback module for ProbOS builds (startup/rollback.py unwinds a failed start; turn_promotion.py promotes conversational turns). verify_and_close has no production caller. FaultReportStore.resolve (fault_report.py:909) has no expected-state check, and when its database write fails it logs and keeps the new status in its cache. /api/health (routers/system.py:35) reports liveness but no release identity.

    Paths that patched the running checkout (closed by BF-897, #1559). WorktreeManager.merge_to_main used to check out main and merge in the repository root, and /api/build/approve (routers/build.py) used to build with the repository root as work_dir. Both now refuse with a reason, and execute_approved_build refuses any work_dir inside the checkout the runtime started from (builder_paths.operator_checkout_refusal). It compares locations, not the repository a .git entry names, and assumes the runtime's environment sets no GIT_DIR or GIT_WORK_TREE; both limits are recorded on #1523. WorktreeManager.remove (worktree remove --force, branch -D) acts on the build's own worktree and branch, not on the operator's checkout. AD-1299 work must still never route through merge_to_main; delivery is the pull-request route (AD-1336 child 6).

    Design references from the retired Supervised Worker Doctor¶

    The retired Doctor solved three problems this epic also has. They are carried as ideas, not code; nothing is copied, ported, imported or wrapped. Each is mapped to its native owner so the epic does not grow a second campaign engine.

    • (a) Isolated repair with verified promotion and rollback. Each attempt in its own worktree with its own identity; preserve operator work; never force cleanup; promote only a clean committed tree into a new immutable install; compare-and-set activation; inspect, never replay, a lost reply; roll back only if the active generation still matches; an unknown rollback blocks. Native owner: S3 (campaign worktrees) and S4 (release controller). Net-new work.
    • (b) Typed incident and rescue records. Versioned typed records with expected-state transitions; unknown is terminal until reconciled; budgets bound attempts. Native owner: the fault and filing owners (FaultReport, fault_issue_filings), CrewSession/WorkItem lifecycle, and AD-1316's operation/attempt identity. No second incident store or state machine.
    • (c) A campaign evidence bundle. Link already-recorded evidence for one candidate to the exact commit and tree; grants no authority; missing proof stays explicitly unavailable. Native owner: the S1 RepairCandidate and evidence-link contract, reusing the gate receipt rather than re-deriving it.

    • Perceive: read scoped diagnostics, existing fault records, source/test evidence, and relevant episodes. Resolve operational paths and release identity from the process/deployment authority, never from a repository-relative guess.
    • Decide: use instructions-driven reasoning to diagnose, classify the work, choose an existing engineering capability, and propose a bounded objective. An agent's classification is a proposal; the Captain's approval is authority.
    • Act: obtain an Architect-reviewed contract, open the campaign as a CrewSession, prepare the candidate as text, request each consequential step through the existing approval surface, and collaborate with Builder, QA, and Red Team within the admitted campaign. No candidate code runs before the Captain approves its exact candidate digest. Deterministic services own transitions; agents own engineering judgment (Design Principle #1).
    • Report: project campaign evidence into existing work/approval surfaces and episodic memory. Distinguish proposed, built, tested, promoted, healthy, rolled back, blocked, failed, and unknown outcomes. A report or a work-item status is not campaign completion; completion is the linked evidence chain below.

    No second durable campaign database or scheduler is introduced. New dependencies use narrow injected protocols; eventual configuration belongs in the existing Pydantic models. Autonomous repair, maintenance, and enhancement admission default to disabled. When an owner is unavailable, diagnosis and proposals remain available; mutation and promotion are blocked with an explicit escalation to the Captain, never a silent refusal (Design Principle #13).

    Separate authority classes¶

    Class Permitted objective Required authority
    Repair Restore an existing approved behavior against a reproduced defect and a discriminating regression test. Captain approval per consequential step, including approval of each exact candidate digest before its code runs. An explicit time-bounded repair delegation (repository, paths, tools, risk, budgets, allowed effects fixed in advance) exists only if the Captain chooses D-B2 option (b) or (c); under the working default (a) there is none. No feature expansion.
    Maintenance Preserve approved behavior through declared upkeep, supported dependency refresh, performance work, or bounded operational maintenance. A separate maintenance grant with compatibility criteria, allowed operations, schedule, and resource limits. A repair grant does not imply it. A scheduled (unattended) grant runs candidate code without per-candidate approval, so it exists only under D-B2 option (b) or (c); under the working default (a) each maintenance campaign is Captain-approved per step, including each candidate digest before its code runs.
    Enhancement Add or intentionally change behavior, capability, public contracts, or architecture. Explicit Captain-approved scope and architecture decision, followed by its own accepted build contract. Neither repair nor maintenance authority implies enhancement authority.

    Authority is checked at admission and every consequential boundary. Expiry, revocation, scope drift, mixed-class changes, or an unclassified effect pauses work for reauthorization; changing a label never widens a grant. Security, governance, deployment-control, and data-migration effects require explicit approval regardless of the proposed class. Destructive mesh intents retain consensus requirements; consensus and trust do not replace Captain approval.

    The agent, Builder, and either backend cannot be granted authority to change approval rules, grants, review requirements, completion criteria, accepted evidence, or the release controller. Changes to the release controller itself are ordinary enhancements under their own Captain-approved AD and review; a campaign cannot weaken the controls judging it. Under the in-envelope design this is enforced by the Captain's per-step decision; recorded evidence digests let a change be detected by a consumer holding an earlier trusted digest; it is not an OS-level write exclusion (that would be D-B2 option (b)).

    Native campaign governance¶

    Replaces the withdrawn SupervisedCampaignAdapter v1. There is no adapter and no external campaign service: each requirement has a native owner.

    Contract area Native owner and v1 semantics
    Identity A repair campaign is one CrewSession parent WorkItem; its id is the campaign key. Each repair attempt is an owned step with its own attempt identity. Backend identity is attempt metadata, never the campaign key. Repository, base commit and candidate identity are the S1 RepairCandidate.
    Lifecycle CrewSession/WorkItem compare-and-set transitions (compare_and_set_recovery, transition_work_item, verification CAS, terminal transition with trust). Effects an attempt produces use AD-1316 operation/attempt identity; unknown is terminal until reconciled and is never replayed.
    Authority The Captain's decision on an action-shaped request in CapabilityRequestStore, bound to the candidate digest, with an expiry, re-checked at each boundary. action requests stay with the Captain alone (delegated_approvals.py:171-172: every action, repair included, is Captain-reserved). The Captain approves each exact candidate digest before its code runs. Agents may prepare candidates as text without approval. Delegated/autonomous grants exist only under D-B2 option (b) or (c); the working default (a) has none.
    Candidate RepairCandidate: base commit, candidate commit, tree, and the reviewed index tree, which must equal the committed tree. A path or branch name alone is not candidate identity.
    Evidence Insert-only evidence links keyed by the candidate digest: gate receipt, review set, Captain approvals, promotion and health observation. Each link is present, refused (contradicts the candidate) or unavailable (cannot be read); anything other than present blocks completion and is never inferred. No raw prompts, credentials, or tool payloads in evidence.
    Recovery Reconcile before retry or backend switch, through CrewSession recovery and AD-1316 reconciliation. Duplicate submissions resolve to the existing operation; no transport-level exactly-once claim.
    Results Distinguish admitted, in progress, blocked/unknown, failed/cancelled, completed and rolled back. Acknowledgement is not execution, execution is not promotion, and a backend's success flag cannot close a campaign.

    Enforced, refused, recorded (repeated because it is load-bearing). Enforced: the Captain decides each consequential step; store transitions are compare-and-set; review records refuse a reviewer equal to the assignee. Refused by the S1 binders: a receipt or review set that contradicts the candidate in the facts they check (commit, tree, status, schema and reviewer independence, plus the label when one is expected). Recorded: a sha256 per piece of evidence. A receipt's covers its supplied raw bytes, so any change to them changes it. A review set's covers only the candidate-bound projection of five review fields (attempt id, reviewer id, assignee id, reviewed tree, accepted): a change to those changes it, a change to any other review attribute (for example a submission digest) does not. A consumer that retained an earlier trusted digest can detect a change only within what each digest covers; an edit to an unread receipt field, or a review re-labelled to another valid independent value, still binds. Not authenticated and not prevented: the producer's identity, and same-OS-identity writes to stores or evidence. Never write "the candidate cannot write X", "every edit is refused" or "the digest covers the whole review" where the platform only records what it records.

    Execution backends: one handoff¶

    Replaces the Worker-dispatched backend model. Both backends already exist and already share one native handoff: a BuildSpec goes in, a list of file changes comes out, and execute_approved_build(work_dir=<campaign worktree>) applies it.

    • Native: NativeBuilderHarness.run_build(spec, work_dir) returns file_changes. Tool calls pass through ToolExecutor, which AD-1316 can govern in strict mode.
    • GHCP: CopilotBuilderAdapter.execute returns file_blocks. Its tools run inside the Copilot SDK with approve_all, outside ToolExecutor. A GHCP attempt is labelled tools not confined, not broker-governed; it requires a per-attempt Captain approval and is never eligible for a delegated grant.

    A backend run that executes code or writes outside the proposal (the native harness's run_command, which its build prompt uses to run pytest, its write_file/edit_file, which accept absolute paths, or any GHCP tool) counts as running candidate code, so it happens only after the Captain approves the exact candidate digest. Before that approval a candidate is produced as text only (file changes returned, not applied) and a deterministic service writes it into the campaign worktree after checking that every path is relative and stays inside the worktree.

    Backend choice must not change campaign identity, authority, review, evidence, completion, promotion, or rollback semantics. Every backend output is a provisional proposal that ProbOS validates, commits in the campaign worktree and identifies by tree hash. GHCP-authored candidates still pass CodeValidator (where applicable), QA, Red Team and independent review. No backend-specific waiver.

    A switch keeps the campaign, operation identity, budgets and history. The prior attempt is reconciled first; an unknown attempt blocks automatic fallback. Only evidence for the exact unchanged candidate can remain current.

    Dual-backend support is claimed only after a real GHCP run of the milestone. Conformance fixtures with a fake SDK prove the handoff, not the backend.

    Isolate, validate, promote, recover¶

    1. Pin and isolate. Record the approved base and active release identities. Create a campaign worktree and constrained execution environment. Preserve existing worktrees and uncommitted changes; never force-remove, reset or stash. No backend may be given write access to the active runtime tree, environment, packages, data, governance state, or deployment selector. Check canonical paths, junctions/symlinks, hard links, subprocess working directories, and tool roots. A worktree is isolation of source changes, not a sandbox for arbitrary build/test code. Never route through merge_to_main, WorktreeManager.remove or the repository-root work_dir of routers/build.py.
    2. Diagnose, prepare and approve. Reuse the existing fault/repair flow, Architect and BuildSpec, and produce the candidate as text (see "Execution backends: one handoff"); a deterministic service writes it into the campaign worktree and commits it, giving one RepairCandidate digest. No candidate code runs before the Captain approves that exact candidate digest, having seen its diff. A change after approval (a fix for a failing test or a review finding) is a new candidate and needs a new approval before its code runs. Assert the reproduction's premise before trusting it. Bind every mutation to the accepted footprint. No active-runtime AgentPatcher, monkey-patching, module reload, live registration, or in-place package update is a maintenance deployment path.
    3. Shadow validation (only for an approved candidate digest). Run a separate candidate process with disposable or verified snapshot-derived data, separate ports/identities, and blocked or explicitly brokered external effects. Prove interpreter/import origins are the candidate, not the parent's editable installation. Apply CodeValidator before every generated/restored agent import, retain sandbox/probation/QA/ behavioral checks, and use repository static/security checks for core code. Do not weaken agent-schema validation to make arbitrary core modules pass. Replaying stored failing arguments requires authority for the operation's effects and an isolated target; a trace is not permission to repeat a live destructive action. Test the intended behavior, not just disappearance of the original error signature.
    4. Freeze and verify (only for an approved candidate digest; the Captain's approval in step 2 is the change approval and precedes all of this). Run focused regressions through affected production consumers, then System QA and Red Team as owned-step reviews (ReviewedStepResult), each by an agent and context different from the builder's. Repairing a finding produces a new candidate, which returns to step 2 for approval before its code runs. Then run the final canonical repository gate. Every review record and the gate receipt must name the same tree, equal to the receipt's tree.head_tree and tree.index_tree; the S1 evidence links refuse anything else. The Builder's internal CodeReviewAgent check is never relabelled as independent review. Any source, test, dependency, configuration, or artifact change invalidates affected evidence. No unresolved Critical/High finding and no missing/unknown required check can pass.
    5. Prepare immutable release. Produce a content-addressed release manifest binding source tree, executable artifacts, locked dependencies, relevant configuration, the evidence-link digest, and the prior known-good release. Verify the staged bytes again before activation: the controller re-derives the expected release bytes from the approved tree id and refuses a staged release that differs. Whether git re-checks object hashes on every read is not verified, so this does not claim to detect a tampered object store. Retain the previous release and a verified recovery path. Irreversible migrations are outside ordinary v1 admission; data-affecting work needs an explicitly approved compatibility and restoration proof.
    6. Promote externally. An out-of-process release controller (a standard-library script under scripts/) activates a release only on an explicit Captain command; the Captain running it is the authorization. It journals intent (append-only, fsynced), checks the expected active generation, and switches an atomic selector (temporary file plus os.replace) or performs a controlled restart. It never overwrites files a running process imported. ProbOS, the Builder and either backend hold no promotion entry point. The controller works while ProbOS is stopped. Moving the Captain's own launch onto the selector is an opt-in deployment change the Captain makes.
    7. Observe and roll back. The controller observes /api/health, extended in S4 to report the active release identity, plus readiness, the targeted repaired behavior, and observation criteria fixed before promotion. Missing or ambiguous health is not healthy. On failure the controller restores the prior immutable release, only if the active generation still matches, and verifies its health; a changed generation or an unknown rollback outcome blocks and escalates. Code rollback is not data rollback: prohibit automatic reuse of incompatible data and escalate when the approved restore procedure cannot safely run. Recovery does not depend on ProbOS being healthy or running.

    Completion requires the chain, not its individual producers: accepted contract, isolated build, current validation and independent review, verified immutable promotion, and passed post-promotion observation, each a present evidence link for the same candidate. Any required remote publication and issue closure must also be read back from their authorities. Rolled back is a recorded outcome, not a successful enhancement. Keep campaign completion separate from build success and from restoring service after failure.

    Record diagnoses, attempted actions, reviewer findings, verification outcomes, promotion, and rollback as linked episodes with evidence references. Trust updates retain raw (alpha, beta) parameters and are idempotent over verified attempted outcomes; no-attempt/blocked outcomes do not earn success credit. Lessons, Hebbian routing, and behavioral monitoring can improve future proposals but cannot modify authority or waive future gates.

    D-B2: reframed 2026-10-11 (partly in-envelope)¶

    Re-run under the standing rule "reframe the requirement before recommending a park" (PR #1507). The original park (admit privileged OS isolation before any delegated or autonomous grant) is replaced by the following.

    What it protects, from whom. It protects the release root, controller, campaign and approval stores and evidence from the code a campaign itself runs (tests, shadow run, GHCP's unconfined tools) and from same-user processes. Nothing on main excludes them: AD-993 is Tier 1, same-user, "NOT a kernel-enforced containment boundary" (execution/isolation.py), and the only tier built (config_models/operations.py); AD-1315/1316 give detection plus confinement of tool calls, and are default OFF. Unlike #1239, the remaining writer is the code under test, so the guarantee cannot simply be narrowed. Captain-per-step approval decides; it does not contain. The real line between per-step and delegated work is AD-1213, which keeps every action (repair included) with the Captain (delegated_approvals.py:171-172), and whether a human approved the exact code before it ran.

    In-envelope now (adopted as constraints; they strengthen a control). - N1, execute-after-approval: no candidate code runs before the Captain approves its exact candidate digest. Agents prepare candidates as text, and a deterministic service writes them into a campaign worktree after checking every path. Any later change is a new candidate needing a new approval. - N3, promotion-time re-derivation: the controller re-derives release bytes from the approved tree and refuses a staged release that differs. Whether git re-checks object hashes on every read is not verified, so N3 does not claim to detect a tampered object store. - N2, optional and Windows-only: the strict broker confines the agent's own tool writes to the campaign worktree and refuses shell effects. That the broker maps run_command to the shell class is not verified here.

    These must never claim containment, end-to-end autonomy, governance the candidate cannot write, or that approval prevents tampering.

    Detection-only, named for S2 (C12): ledger reset by deleting the file. The S1b evidence ledger (repair_evidence.db) detects a changed digest only for a reference the consumer re-presents, and only while the file exists. A writer with ProbOS's own OS identity can delete the file; start() then creates an empty ledger and the first digests are gone without a signal. This is neither refused nor prevented. S2 wiring must decide how a recreated ledger is detected (for example a ledger identity recorded at campaign admission) and must derive a fresh reference per gate run (prompts/ad-1299-s1b-evidence-completion-ledger.md, "Blind spots named").

    The Captain's decision. May a campaign run candidate code or advance a repair action without your approval of that exact candidate? (a) No: keep execute-after-approval (recommended, and the working default S1-S4 build under). (b) Yes, inside an admitted isolation AD (separate owner UID or AD-995 Tier 2) plus a scoped AD-1213 amendment. (c) Yes, uncontained, scoped and expiring (not recommended). Narrower delegation limited to reversible classes (for example test- or docs-only diffs) is also the Captain's: it changes the AD-1213 floor. After (a) nothing further is needed; after (b) or (c), S2b adds delegated repair grants and scheduled maintenance grants.

    Prior art and blind spots (2026-10-11)¶

    A bounded review (the standing "anything not considered, or prior work to leverage" pass, PR #1505) found no change to the rescope or to S1a. Evidence links follow the shape of an in-toto Statement, a typed kind bound to a subject digest, without its signing envelope: a hash is integrity, not authenticity (AD-1047), so no envelope is emitted until key infrastructure exists. S1a's 40/64-hex commit and tree ids are the in-toto gitCommit/gitTree DigestSet shapes. The release controller adopts update-framework and boot-assessment lessons: a monotonic activation sequence (not release identity) for compare-and-set, fail-closed on absent state, verify before persisting, an indeterminate then good or bad release status with bad never auto-selected, retention that keeps the active and rollback releases, and validation in the release's own environment. TUF role signing and OS-level deployment were considered and rejected or deferred: they need keys or privilege (D-B2 option (b), the Captain's) and add nothing against a writer with ProbOS's own OS identity. The full table, with sources and what was absorbed, adapted, rejected or deferred, is in prompts/ad-1299-s1a-repair-candidate.md. Review round 1 of S1a (Amendment 1) separately corrected the binding's claim to "refuses what contradicts the candidate in the facts it checks; records a sha256 per piece of evidence", and round 2 scoped that digest (a receipt's raw bytes; a review set's five projected fields only) (see "Native campaign governance").

    Named constraints for later slices (acceptance criteria, not new scope):

    Id Slice Constraint
    C8 S1b The review binder takes a required expected_assignee (the campaign's builder) and refuses a set in which any review names a different assignee. Built in S1b.
    C9 S1b A required-evidence-kinds set per authority class. Completion means every required kind is present for the same candidate digest; extra kinds never substitute. Built in S1b.
    C10 S2/S4 Two independent requirements for forward promotion: base_commit equals the approved base, and candidate_commit descends from the active release's commit. Promotion refuses if either fails. A recovery rollback to a retained release is a separate path governed by C1 and C4.
    C11 S3 Every regression probe that passes on the active release must also pass on the candidate (comparison with the incumbent).
    C1 S4 Activation compare-and-set keys on a monotonic, never-reused activation sequence. A rollback is a new sequence entry pointing at the old release.
    C2 S4 An absent, unreadable or zero journal or generation blocks activation and rollback; there is no default value.
    C3 S4 The controller records a new active state only after staged-byte verification and the generation check pass. Test: a failure injected between verify and persist leaves the prior state unchanged.
    C4 S4 Release status is indeterminate, then good or bad. Only the observation window promotes to good, and a bad release is never auto-selected.
    C5 S4 Liveness from /api/health alone is never "healthy". Readiness plus the repaired-behavior probe are required.
    C6 S4 The release environment is built from the tree's uv.lock. The manifest records the interpreter version and an installed-environment digest, and shadow validation runs in that environment.
    C7 S4 Garbage collection never removes the active release or the rollback target. Release trees share no hard links with mutable paths, and staged bytes are re-hashed before activation.
