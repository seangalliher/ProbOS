# AD-853..857 — Crew Self-Unblock: unified CapabilityRequest, acquire-vs-build triage, block→resume loop

**Status:** Draft for review (Architect-authored, verify-first against HEAD)
**Mode:** Architect spec. Builder executes ONE AD = ONE commit with a gate between each. Do NOT build the whole epic in one pass.
**Northstar:** Crew agents function like a ship's crew — commanded by conversation or formal assignment, all work tracked on the kanban board through its lifecycle, agents get work done with their knowledge/skills/tools, and when blocked they **request approval to acquire a tool/skill or to have a new capability built** rather than silently failing.
**Numbering:** Highest committed AD = **AD-839**. This epic = **AD-853–857** (845–852 reserved for Yeo workflow + web-research depth; 840–844 for Desktop Console). Reconciled in `docs/development/roadmap.md` (Crew Autonomy table).

## Why this epic (the gap)

Every individual primitive already exists, but as **four disconnected approval mechanisms** with no shared model, queue, or auto-resume:

| Existing primitive | Location (verified HEAD) | Limitation |
|---|---|---|
| Vision-capability proposal (agent→Captain approve/deny) | `propose_vision_capability` [routers/agents.py:847](../src/probos/routers/agents.py); `ProposeVisionCapability` [api_models.py:345](../src/probos/api_models.py); `VisionProposalEntry` sidecar | Vision only |
| In-chat tool grant | `ChatToolGrantRequest` [api_models.py:328](../src/probos/api_models.py); `chat_tool_grant` [routers/chat.py:1020](../src/probos/routers/chat.py); `ToolPermissionStore.issue_grant` (VERIFY signature — sibling of `ClearanceGrantStore.issue_grant` [clearance_grants.py:105](../src/probos/clearance_grants.py)) | Captain-initiated, not agent-requested |
| Self-mod build approval | `require_user_approval` + `_user_approval_fn` + `_import_approval_fn` [self_mod.py:129-214](../src/probos/cognitive/self_mod.py) | Bare callback, jumps straight to "build new agent" |
| Extension install approval | `PENDING_APPROVAL` → `approve_extension` [extensions/registry.py:55-97](../src/probos/extensions/registry.py) | Separate state machine |
| Work-item BLOCKED state | `WorkItemStatus.BLOCKED` + transitions `in_progress↔blocked` [workforce.py:51,165-218](../src/probos/workforce.py) | Nothing DRIVES it; no resume |

**Net:** an agent that hits a wall today just fails. There is no single "I need capability X, here's why, here's the task it unblocks" request, no cheap-first triage (grant before build), and no driver that sets the WorkItem `BLOCKED`, files the request, and resumes on approval. That spine is this epic.

## AD-853 — Unified `CapabilityRequest` model + single approval queue

**Build.** A new module `src/probos/capability_request.py`:
- `@dataclass CapabilityRequest`: `id`, `agent_id`, `kind: Literal["grant","install","build"]`, `target` (tool_id / skill name / capability description), `rationale` (≤280, matches AD-718a budget), `work_item_id: str | None`, `status: Literal["pending","approved","denied","fulfilled","failed"]`, `created_at`, `decided_at`, `decided_by`, `decision_reason`.
- **Identity & attribution (required).** The request is attributable to the requesting agent's stable **`AgentID`** (`agent.id`, a `str` from [types.py:13](../src/probos/types.py); this is the trust-boundary key every store + `TrustNetwork` consumes — do NOT pull in the `identity.py` DID/birth-certificate ledger, that is a different concern) so the approval trail records *whose authority the capability was granted under* — and the outcome (approved/denied/fulfilled/failed) is recorded against that agent's **trust ledger** so capability requests feed the learning loop (a denied or failed request is a trust signal, an approved-and-fulfilled one is provenance). Record via the **verified-real** signature (sync, keyword args): `trust.record_outcome(agent_id=req.agent_id, success=approved, weight=1.0, intent_type="capability_request", source="capability_request")` — real def is `def record_outcome(self, agent_id, success, weight=1.0, intent_type="", episode_id="", verifier_id="", source="verification") -> float` ([trust.py:217](../src/probos/consensus/trust.py); it is **synchronous**, do NOT await it, and there is NO positional `source` — use keywords). Do NOT add a new identity system or a new attribution scheme — reuse the existing per-agent `AgentID` + `TrustNetwork`. The `decided_by` field captures the approver (Captain) for the dual-attribution audit trail.
- `class CapabilityRequestStore` following the verified `ClearanceGrantStore` DB+cache shape [clearance_grants.py:105-145](../src/probos/clearance_grants.py): `async def file_request(...) -> CapabilityRequest`, `async def decide(request_id, approve, reason, decided_by) -> CapabilityRequest`, `async def list_pending()`, `async def get(request_id)` (the read methods do DB I/O — they MUST be `async`, mirroring the sibling's async `list_grants`/`get_grant`; do NOT leave them sync). - **Event emission (the sibling does NOT do this — AD-853's one legitimate divergence).** `ClearanceGrantStore`/`ToolPermissionStore` `issue_grant` emit **no events**; mirroring them "exactly" yields zero events and fails the acceptance test. Add emission via the existing `EventEmitterMixin` ([protocols.py:20](../src/probos/protocols.py)): accept an `emit_event` callback at construction, set `self._emit_event`, and call `self._emit(EventType.CAPABILITY_REQUEST_FILED, {...})` / `CAPABILITY_REQUEST_DECIDED` / `CAPABILITY_REQUEST_FULFILLED` at the right points. The callback is wired in `startup/communication.py` at construction.
- New events in [events.py](../src/probos/events.py) (the mechanism is the `class EventType(str, Enum)` at [events.py:21](../src/probos/events.py) — add members, e.g. `CAPABILITY_REQUEST_FILED = "capability_request_filed"`; verified-existing siblings `WORK_ITEM_CREATED`/`WORK_ITEM_STATUS_CHANGED` at [events.py:98-100](../src/probos/events.py); do NOT assume any others exist): `CAPABILITY_REQUEST_FILED`, `CAPABILITY_REQUEST_DECIDED`, `CAPABILITY_REQUEST_FULFILLED`.
- Wire the store in startup alongside the other stores: construct `CapabilityRequestStore(db_path=str(data_dir / "capability_requests.db"), connection_factory=..., emit_event=<runtime emit>)` immediately after the `ClearanceGrantStore` block at [startup/communication.py:291](../src/probos/startup/communication.py), `await ...start()`, no config gate; declare `runtime.capability_request_store: CapabilityRequestStore | None = None` alongside [runtime.py:702](../src/probos/runtime.py).

## AD-854 — Acquire-vs-build triage router (grant → install → build)

**Build.** `src/probos/cognitive/capability_triage.py` — a **pure** decision core (no I/O, deterministic over plain data) + a thin async driver that does all the I/O:
- **Pure** `triage(*, tool_registered: bool, agent_has_permission: bool, skill_known: bool) -> Literal["grant","install","build"]` — cheapest reversible rung from three already-resolved booleans, mapped to the three governance axioms (real named concepts; do NOT invent):
  1. **grant** — a registered tool the agent lacks permission for (`tool_registered and not agent_has_permission`) → **Minimal Authority** (most reversible, no new code).
  2. **install** — a known skill/extension (`skill_known`) → **Reversibility Preference** (sandboxed, revocable).
  3. **build** — otherwise → **Safety Budget** (most expensive/least reversible; always needs Captain approval).
  Do NOT type the input as a `CapabilityGap` dataclass — **no such type exists** and the footer forbids inventing one. The real gap surface is a plain `str` (`runtime._last_capability_gap` / the unhandled-intent name); the driver resolves it into the booleans above before calling `triage`.
- **Pure** `evaluate_grant_fast_path(*, non_destructive: bool, peer_precedent: bool, agent_trust: float, trust_floor: float, fast_path_enabled: bool) -> bool` — the three predicates ANDed and config-gated. `install`/`build` never call this.
- **Zero-ceremony fast path for the grant rung (low-latency case).** A `grant` MAY be **auto-approved without a Captain prompt** when ALL hold: (a) the target tool is **non-destructive** — derive this from the tool's required **`ToolPermission`** level (`OBSERVE`/`READ` = non-destructive; `WRITE`/`FULL` = destructive; use `permission_includes()` / the `ToolPermission` ordering in `tools/protocol.py`). Do NOT use `IntentDescriptor.requires_consensus` here — that field lives on **agents/intents**, not tools, and a grant target is a `tool_id`. (b) an **in-department peer already holds** the grant (precedent) — the driver computes this by `ToolPermissionStore.list_grants(active_only=True)` filtered to the `tool_id`, mapping each holder to its department via `ontology.get_agent_department(agent_type)`; there is no single by-tool query, compose it. (c) the requesting agent's trust is at/above a configurable floor — read from **`runtime.trust_network.get_score(agent_id) -> float`** (trust.py:406, sync, Beta-mean 0–1), NOT from the AD-853 store's trust hook (left `None` at startup). Otherwise the grant falls back to the normal approval queue. `install` and `build` ALWAYS require Captain approval — no fast path. The auto-approve decision and its three predicates are logged and recorded against the agent's trust ledger. Make the floor + the whole fast path config-gated (new Pydantic model + `SystemConfig` field, sibling pattern `ConsultationDispatchConfig`; default conservative — fast path OFF or trust-floor high until proven).
- **Async driver** `triage_and_file(*, gap_target: str, agent_id: str, ...stores) -> CapabilityRequest` — gathers the booleans (`tool_registry.get(tool_id) is not None`; permission via `ToolPermissionStore.get_active_grants_sync(agent_id, tool_id)`; `extension_registry.get_manifest(...) is not None`), peer-precedent, and trust; calls the pure functions; files via `store.file_request(...)` (AD-853, carries `work_item_id`); and on approval (auto or Captain) routes to the existing fulfiller for that rung: grant→`ToolPermissionStore.issue_grant` (`async def issue_grant(self, agent_id, tool_id, permission: ToolPermission, *, is_restriction=False, reason="", issued_by="captain", expires_at=None) -> ToolAccessGrant`, permissions.py:110); install→`approve_extension(extension_id)` (extensions/registry.py:96); build→`self_mod_pipeline.handle_unhandled_intent(...)` (self_mod.py:96 — note it ALREADY has its own `require_user_approval` gate; compose, do NOT double-prompt). On fulfilment, mark the request `fulfilled`: add a small `async def mark_fulfilled(self, request_id) -> CapabilityRequest` to the AD-853 `CapabilityRequestStore` (emit `CAPABILITY_REQUEST_FULFILLED`) — the only AD-853 store addition AD-854 makes. Honest-degrade to `build` (logged reason) when registries/trust are absent.
- Reuse the existing capability-gap surface (`is_capability_gap(response: str) -> bool` [decomposer.py], `runtime._last_capability_gap: str`) — do NOT invent a new gap detector or a `CapabilityGap` type.

**Acceptance.** `tests/test_ad854_capability_triage.py` (≥7): the pure-function cases need NO fixtures — missing-permission-on-registered-tool→grant; known-skill→install; novel→build; build always sets needs-approval; **`evaluate_grant_fast_path` truth table — auto-approves only when non-destructive + peer-precedent + trust≥floor + enabled all hold, else False**; `triage` pure/deterministic given inputs. The async-driver cases (file + route-to-fulfiller + mark_fulfilled) use a **real `CapabilityRequestStore` fixture + real `TrustNetwork`** (copy the fixture from `tests/test_ad853_capability_request.py`, NO MagicMock at the storage boundary); unknown registries→honest-degrade to build with a logged reason. Verify all changes comply with the Engineering Principles in `.github/copilot-instructions.md`.

**Do NOT build:** the resume driver (855), new fulfillers (reuse existing), UI.

## AD-855 — BLOCKED → request → approve → resume work-item loop driver

**Build.** A `CapabilityGapDriver` (new module `src/probos/cognitive/capability_gap_driver.py`) that closes the lifecycle on the kanban board. **There is no pub/sub bus** — stores emit via `EventEmitterMixin._emit → self._emit_event(event_type, data)`; the real subscribe surface is `runtime.add_event_listener(fn, event_types=[...])` (runtime.py:1118), and listeners receive the **envelope** `{"type", "data": {...payload...}, "timestamp"}` (read `event["data"][...]`, exactly like `WorkItemRouter.on_work_item_created`). Two **public** entry points (so AD-855 is independently testable without the AD-856 executor):

- `async def on_capability_gap(self, *, work_item_id: str, gap_target: str, agent_id: str) -> CapabilityRequest | None` — the BLOCK + file step. The block path must NOT use a single `update_work_item(status=..., metadata=...)` call: `update_work_item` REPLACES metadata (`json.dumps`, no merge) and bypasses transition validation, which would clobber `metadata["dispatchable"]` (silently breaking the later re-dispatch) and skip the state machine. Required sequence:
  1. `await store.transition_work_item(work_item_id, "blocked", source="capability_gap_driver")` (validated; `in_progress→blocked` is legal for all built-in work types; `transition_work_item` takes NO metadata).
  2. read-merge-write metadata: `item = await store.get_work_item(work_item_id)`; `merged = {**(item.metadata or {}), "blocked_reason": gap_target, "capability_request_id": req.id}`; `await store.update_work_item(work_item_id, metadata=merged)` (never pass a bare dict).
  3. file the triaged request: `await triage_and_file(..., work_item_id=work_item_id)` (AD-854 driver; carries `work_item_id`).
- `async def on_capability_event(self, event: dict) -> None` — the resume/fail handler, subscribed to **both** `CAPABILITY_REQUEST_FULFILLED` and `CAPABILITY_REQUEST_DECIDED`. **Resume on FULFILLED, not on approved** ("approved ≠ available": the grant/build/install isn't usable until fulfilled, and the fast path emits DECIDED(approved) *before* `issue_grant`, so resuming on approved would re-dispatch into the same gap → infinite block/approve/block loop):
  - the DECIDED/FULFILLED payloads do **NOT** carry `work_item_id` — recover it: `req = await store.get(event["data"]["id"])`; `work_item_id = req.work_item_id if req else None`.
  - on `CAPABILITY_REQUEST_FULFILLED`: `await store.transition_work_item(work_item_id, "in_progress", ...)` then **re-dispatch** by mirroring the router's create path (there is NO `WorkItemRouter.dispatch()`): `item = await store.get_work_item(work_item_id)`; `await runtime.work_item_router.on_work_item_created({"type":"work_item_created","data":{"work_item": item.to_dict()},"timestamp": time.time()})`.
  - on `CAPABILITY_REQUEST_DECIDED` with `event["data"]["status"] == "denied"`: `await store.transition_work_item(work_item_id, "cancelled", source="capability_gap_driver")` (NOTE: `blocked→failed` is **illegal** for every built-in work type and would silently no-op; the deny terminal is `cancelled`) and write the denial reason to metadata via the read-merge-write pattern above.
  - **Idempotent**: re-read the work item and act only if its current status is still `blocked` (the fast path fires DECIDED(approved) AND FULFILLED for the same request; the approved DECIDED must be a no-op). Honestly note: a build that never goes active, or a Captain-approved install never marked fulfilled, leaves the item BLOCKED — correct degrade, not a bug.
- Hold all task references (no fire-and-forget — the `add_event_listener`/NATS path already tracks handler tasks; the driver itself must not spawn untracked tasks). Honest-degrade (log-and-degrade, no raise) if `work_item_router`/stores are absent. Wire the driver + its `add_event_listener` registration at startup alongside the AD-853 store (confirm the exact startup module; mirror the AD-581a listener wiring at finalize.py:1717-1736 — `getattr` + try/except log-and-degrade).

**Acceptance.** `tests/test_ad855_block_resume.py` (≥6, **real** WorkItemStore + CapabilityRequestStore — NO MagicMock at the storage boundary; a mock would let illegal transitions and metadata-clobber pass green; copy the `WorkItemStore(db_path=str(tmp_path/"wis.db"))` fixture from tests/test_workforce.py:47): (1) gap→BLOCKED with **merged** metadata + `dispatchable` preserved + request filed carrying `work_item_id`; (2) FULFILLED→in_progress + re-dispatch invoked via `on_work_item_created`; (3) DECIDED(denied)→cancelled with reason; (4) DECIDED(approved) on an already-blocked item is a **no-op** (idempotency / fast-path double-event); (5) store/router absent→log-and-degrade, no raise; (6) `work_item_id` recovered via `store.get()` when the payload omits it. Verify all changes comply with the Engineering Principles in `.github/copilot-instructions.md`.

**Do NOT build:** UI, the AgenticLoop bridge (856) — AD-855's `on_capability_gap` is the seam 856 will later call.

## AD-856 — `AgenticLoop` as the executor for dispatchable work items (bridge)

> **Architect corrections applied (verify-first review, NO-GO → GO).** Every cited API verified real at HEAD (no phantom APIs), but four hot-path gaps were closed: (1) the denial→gap mechanism did not exist — `AgenticLoop.run` swallows the `ToolPermissionDenied` raise into an `is_error` tool-result and `AgenticResult` carries no tool results, so a capture wrapper is now specified; (2) "mesh intents as tools" is greenfield (AD-852 is **not built** — no copy source) and is now an explicit, in-scope thin adapter; (3) a conservative config feature-gate + automatic fallback to the existing path is now required; (4) the real dispatch seam is `await self.handle_intent(dm)`, not `act()`, and the non-dispatchable regression lives at the router boundary.

**Build.** Today a dispatched work item runs `_handle_work_item_dispatch` ([cognitive_agent.py:1082](../src/probos/cognitive/cognitive_agent.py)), which calls `result = await self.handle_intent(dm)` once (single-shot direct-message handling) — the agent can fetch once and answer once but cannot iterate across tools. Wire the existing `AgenticLoop` (AD-545, [swe_harness/agentic_loop.py:47](../src/probos/cognitive/swe_harness/agentic_loop.py)) as the execution path:

- **AgenticLoop is injected, reuse it as-is.** Real ctor: `AgenticLoop(*, llm_client, tool_executor, max_iterations=25, token_budget=None, event_emit_fn=None, tier="deep", ...)`; real run: `async def run(*, system_prompt, user_message, tools: list[dict], context: dict) -> AgenticResult`. The loop is bounded and **never raises** (errors become `is_error` tool-results). Do **NOT** change AgenticLoop internals.
- **ToolExecutor scoped to GRANTED tools.** Real ctor: `ToolExecutor(*, registry)`; real call: `async def invoke(agent_id, tool_id, params, **kwargs) -> ToolResult`. Scope the agent's tools via `runtime.tool_permission_store.get_active_grants_sync(agent_id)` ([permissions.py:178](../src/probos/tools/permissions.py), **sync**, returns `list[ToolAccessGrant]`) → the granted `tool_id`s become the loop's `tools` list.
- **Denial-capture seam (Correction 1 — this is how the gap surfaces).** A tool-permission denial is `ToolPermissionDenied` raised inside `check_and_invoke` ([registry.py:300](../src/probos/tools/registry.py)); `AgenticLoop` catches it, turns it into an `is_error` tool-result, and **continues** — so the caller cannot see it in `AgenticResult`. AD-856 therefore introduces a **thin `ToolExecutor` wrapper/subclass** (`DispatchToolExecutor`) whose `invoke` catches `ToolPermissionDenied`, **records the denied `tool_id` into a `denied_tools` list**, then re-raises (so the loop's existing handling is unchanged). After `run()` returns, `_handle_work_item_dispatch` reads `executor.denied_tools`; for each, it calls AD-855's seam `await runtime.capability_gap_driver.on_capability_gap(work_item_id=<from intent.params>, gap_target=<denied tool_id>, agent_id=self.id)`. Null-guard `capability_gap_driver` (default `None`).
- **Mesh web intents as tools (Correction 2 — explicitly in-scope plumbing).** `web_search`/`read_page`/`http_fetch` exist only as **bus intents**, not registered Tools, and **AD-852 is not built** (no proven adapter to copy). AD-856 builds a **minimal intent→Tool adapter** that registers thin Tool wrappers which `await runtime.intent_bus.broadcast(...)` the corresponding intent and return the result as a `ToolResult`. This adapter is the ONLY new tool-shaped code permitted by this AD; it is plumbing for the loop, not net-new capability.
- **Feature gate + fallback (Correction 3).** Add `AgenticDispatchConfig` to `config.py` (`enabled: bool = False`, conservative per convention #14) on `SystemConfig`. `_handle_work_item_dispatch` runs the loop ONLY when `config.agentic_dispatch.enabled` AND `self._llm_client`, `runtime.tool_permission_store`, and `runtime.capability_gap_driver` are all wired; otherwise it falls back to the existing `await self.handle_intent(dm)` path. **Preserve** the existing thread-logging and the `transition_work_item(..., "in_progress")` behavior on both paths.

This is the single change that makes "agents get work done using their skills and tools" real. Reuse the loop, do NOT author a second one (DRY).

**Acceptance.** `tests/test_ad856_agentic_dispatch.py` (≥5): (1) gated-on dispatchable item runs the loop with ≥2 tool iterations (fake injected `ToolExecutor` + mock LLM); (2) `ToolPermissionDenied` mid-loop → `denied_tools` captured → `on_capability_gap` invoked with the denied `tool_id` as `gap_target`; (3) respects `max_iterations` / token budget; (4) gate-off OR unwired deps → falls back to `handle_intent` (regression, existing path unchanged); (5) `get_active_grants_sync` set scopes the executor's tool list (use a **real** `ToolPermissionStore` fixture, not MagicMock — substrate-boundary rule). Verify Engineering-Principles compliance.

**Do NOT build:** UI, any tool other than the three mesh-intent adapter wrappers, changes to AgenticLoop internals, changes to triage/resume logic.
